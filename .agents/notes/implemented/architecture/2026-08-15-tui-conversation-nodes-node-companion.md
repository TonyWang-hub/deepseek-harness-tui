# Agent Note: `dsh-tui-runtime` reaches the Chat business Definitions through a `./conversation-nodes` Node companion

Status: implemented

English | [中文](2026-08-15-tui-conversation-nodes-node-companion.zh.md)

## Problem

`packages/tui/runtime`'s dual-context bootstrap mounts the Client halves of `connection`, the Typert registry, the Typert Remote, and the client Runtime object layer through their `./client-node` Node ESM companions ([official-terminal-application](../../proposed/feature/2026-08-15-official-terminal-application.md)). That Runtime object layer provides `ctx.conversationEvents`/`ctx.conversationViews` — the registries a `ConversationNodeDefinition`/`ConversationViewDefinition` populates — but nothing in the composition ever registered into them.

`cordis-yml-file-boot.client.spec.ts` proved the consequence directly: every transcript-content field on `ConversationSnapshot` (`nodes`, `chat.order`, `turnTimings`, `turnEnds`) mirrors `ChatSnapshot.legacy` (`packages/client/runtime/src/client/sessions/conversation.ts`'s `LegacyConversationSlice`), which only a registered Definition populates — these are not an engine-level raw-log tracker independent of business Definitions, despite reading like one from their names and doc comments alone. With no Definition registered, a scripted turn through the full dual-context boot left the client-side sessions face exposing only session lifecycle (`running`, `pending`, `queue`, `openState`); the test could only recover the final assistant text by independently listening to the Host tree's own `session/event` stream, never the client face a real terminal renderer would read.

The Chat business Definitions and their `ChatSnapshotBuilder` target builder already exist and are already pure — `packages/client/ui-conversation/src/client/conversation-nodes/` (`register.ts` plus every module it imports) and `packages/client/ui-conversation/src/client/contract/chat-nodes.ts` carry zero `.tsx`/React imports. The rest of that package is not pure: `src/client/apply.ts` and `src/client/index.ts` (the `./client` entry `apply.ts` re-exports through) reach `.tsx` components (`InputBar`, `ChatView`, …), so neither can load under plain Node.

## Decision

`dsh-client-ui-conversation` gains a `./conversation-nodes` export subpath, publishing ONLY the `conversation-nodes` subtree's compiled entry point (`register.ts`, exporting `registerConversationNodes`) as a plain Node ESM module — never the package's `./client` entry or its root, both of which reach the React closure. The subpath's `types` target resolves to `lib/types/client/conversation-nodes/register.d.ts` (the existing client-face tsc pass's output); its `default` target is a new tsdown companion (`conversationNodesCompanion` in `packages/client/ui-conversation/tsdown.config.ts`) built the same way `dsh-client-connection`'s `clientNodeCompanion` builds `./client-node` — ESM, `platform: 'node'`, no dts, entry pinned to the already-emitted `.js`, never the `.ts` source.

`packages/tui/runtime/src/index.ts` imports `registerConversationNodes` from `@deepseek-ai/dsh-client-ui-conversation/conversation-nodes` and calls it directly against the root `clientCtx` immediately after mounting the client Runtime plugin (`clientCtx.plugin(runtimeClient)`), which is what provides `ctx.conversationEvents`/`ctx.conversationViews`. `registerConversationNodes` ties every registration's disposal to `ctx.effect()` on whichever Context it is called with, so calling it on the root `clientCtx` — rather than wrapping it in its own `ctx.plugin()` — disposes the registrations together with the whole client tree's own teardown (`clientCtx.fiber.dispose()`), with no separate plugin scope needed for a function that is not itself a named plugin.

Two workspace-wide gates needed the same shape of exemption `./client-node` already has: `tsconfig.base.json` gains a `@deepseek-ai/dsh-client-ui-conversation/conversation-nodes` paths alias resolving directly to `register.ts` (source-plane resolution, matching every other `/client-node` alias), and the Typert generator's `hostExportSubpaths`/`clientExportSubpaths` (`packages/typert/generator/src/analyzer.ts`) treat `./conversation-nodes` exactly like `./client-node` — excluded from the Host-face analysis pass (whose program excludes `packages/client/*/src/**`) and included in the Client-face pass.

`cordis-yml-file-boot.client.spec.ts`'s scripted-turn assertions now read the final assistant text and non-empty `nodes`/`chat.order`/`turnEnds`/`turnTimings` straight from the client-side sessions face, replacing the Host-`session/event`-stream fallback the ASSEMBLY-GAP finding required.

## Alternatives considered

**Extract a new `packages/client/conversation-model` package** (the `official-terminal-application` note's original "Model extraction" plan) — deferred, not rejected: physically moving `ChatSnapshotBuilder`, the Chat Definitions, and `contract/chat-nodes.ts` into a platform-neutral package is the eventual shape once the input machine and popup select controller extract alongside it, but it touches every current importer of `dsh-client-ui-conversation`'s conversation-node types (`declare module` augmentations included) for a landing slice that only needs one function callable from plain Node. The narrower companion ships the same capability with a one-file addition and no import-path churn across the rest of the package graph; the full extraction remains available as a later, independent change.

**Publish the whole `./client` entry as `./client-node`, matching the existing pattern exactly** — rejected: `src/client/index.ts` (compiled to the `./client-node` precedent's target) re-exports `apply.ts`, whose import closure reaches `.tsx` React components. That precedent's own analyzer exemption comment already narrates why: the Host-face program excludes `packages/client/*/src/**`, and the same file resolves fine under the Client-face program only because the whole client half is proven browser-safe elsewhere — a property this package's `./client` entry does not have.

**Wrap `registerConversationNodes(clientCtx)` in its own `clientCtx.plugin({ apply: registerConversationNodes })`** — rejected: `ctx.effect()` inside the Definition registries already ties disposal to whatever Context calls them; a bare direct call against the root `clientCtx` (mirroring the existing bare `clientCtx.remote.$mount(commandsRemote)` call in the same function) achieves identical lifecycle coupling with one fewer indirection, since `registerConversationNodes` is a plain function, not a named plugin with its own `apply`/`inject`/`name` contract.

## Consequences

A scripted turn through the full dual-context Loader boot now produces a non-empty `ConversationSnapshot` on the client-side sessions face — the shape a terminal renderer will actually read — closing the gap `cordis-yml-file-boot.client.spec.ts` recorded. The `./conversation-nodes` subpath is additive: it changes no existing export, and `dsh-client-ui-conversation`'s browser bundle is unaffected (the companion is a separate tsdown config entry sharing the same already-emitted `lib/types` output). The package invariant that a UI plugin's `.` export stays a closed surface ([packages/client/AGENTS.md](../../../../packages/client/AGENTS.md)) does not constrain this addition: the new value export is a Node-only companion subpath consumed by a different package (`dsh-tui-runtime`), not a widening of what the Loader-facing `.`/`./client` entries expose.

The full "Model extraction" package move remains open work; when it lands, this subpath either becomes a thin re-export of the new package or is retired in favor of importing the new package's own Node companion directly — either way, `dsh-tui-runtime`'s call site (`registerConversationNodes(clientCtx)`) is expected to stay a one-line change.
