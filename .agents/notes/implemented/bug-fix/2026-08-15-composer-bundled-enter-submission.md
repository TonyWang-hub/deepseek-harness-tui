# Agent Note: The composer submits an Enter byte merged into a bulk `useInput` event

Status: implemented

## Problem

`dsh --profile tui` against the real DeepSeek API deterministically reproduced: composer ready, a full prompt written to the pty in one call (text ending in `\r`), then zero response for the full wait bound — no streaming, no spinner, no error — with the typed text still sitting in the composer row. The same renderer's own pty smoke test (`packages/tui/runtime/tests/pty-smoke.client.spec.ts`) stayed green because it writes the prompt text and `\r` as two separate `shell.write()` calls with a delay between them, and `packages/tui/ink-ui/tests/components/Composer.spec.tsx`'s own "Enter submits" test does the same split.

Root cause: Ink's `useInput` (`ink/build/hooks/use-input.js`) invokes its handler once per raw stdin chunk, and its own JSDoc says so directly — "if the user pastes text and it's more than one character, the callback will be called only once, and the whole string will be passed as `input`." Ink's input parser (`ink/build/input-parser.js`'s `parseKeypresses`) splits a chunk into escape sequences and individual backspace bytes, but leaves any other run — including an embedded or trailing `\r`/`\n` — as ONE unsplit string, because those bytes can legitimately appear inside pasted text. Ink's `parseKeypress` only sets `key.return` when the ENTIRE chunk is the single byte `\r` (`s === '\r'`). `packages/tui/ink-ui/src/input/edit-model.ts`'s previous `mapKeyToAction(input, key)` decided purely from `key.return`/`key.shift`/exact single-character checks, so a merged chunk like `"hello\r"` — the exact shape one `write()` call carrying "prompt text, then Enter" produces (an automation driver, a paste, or a terminal delivering a fast keystroke burst as a single `read()`) — fell through every branch to the default `{ type: 'insert', text: input }`: the whole string, `\r` included, was inserted as literal text. Enter was silently swallowed; nothing ever called `SessionFace.prompt()`; the text stayed in the composer with no visible error, matching the field symptom exactly.

## Decision

`edit-model.ts` replaces `mapKeyToAction` with `foldKeypressEvent(state, input, key): KeypressFold` (`{ state, submissions }`). A single already-decoded special key (`key.return`, an arrow, backspace, Escape, a Ctrl/Meta combo) still takes the direct path Ink's own decoding recognized, unchanged from before. When `input` carries no `\r`/`\n` at all, it is one plain `insert`, also unchanged. Only a run containing `\r` or `\n` is walked character by character: a bare `\r` (not immediately followed by `\n`) submits the composer's current text and clears it — so any characters after it in the same run continue into a fresh composer — a `\n` (or the second half of a `\r\n` pair, kept as one newline so pasted Windows-style line endings do not each fire a spurious submit) inserts a newline, and every other run of characters between control bytes is one `insert`. `Composer.tsx`'s `useInput` handler calls `foldKeypressEvent` directly against its own `useReducer` state, dispatches every submission's text to `onSubmit`, and folds the resulting state back in through one new `ComposerAction` variant, `{ type: 'replaceState'; state }`, added to `composerReducer` alongside its existing per-transition cases (which `foldKeypressEvent` still calls internally for each step of a batch, so their own tests and semantics are untouched).

## Alternatives considered

**Detect and reject multi-character input containing `\r` as an error.** Rejected: a merged run carrying an Enter byte is an ordinary, expected shape (any fast burst, paste, or automation input), not a malformed one; refusing to submit would just move the same bug's user-facing symptom from "silent" to "silently different."

**Fix this at the Ink/`useInput` layer (a wrapper that re-splits merged chunks before calling the app's handler).** Rejected: Ink's own behavior here is documented and deliberate (a whole pasted string arrives as one event by design); re-splitting a chunk after Ink has already decoded it into `(input, key)` would need to re-derive raw escape-sequence boundaries this package does not own, where `edit-model.ts` already owns exactly this composer's line/submit semantics.

## Consequences

`Composer`'s `useInput` handler now folds a batch of transitions (potentially several inserts, newlines, and submits) from one Ink event instead of mapping it to at most one transition; `composerReducer`'s existing cases are unchanged and still individually unit-tested, plus a new `replaceState` case. Regression coverage: `packages/tui/ink-ui/tests/input/edit-model.spec.ts`'s `foldKeypressEvent` suite (including two `REGRESSION:`-prefixed cases with ASCII and CJK text merged with a trailing `\r`, a mid-run `\r`, a `\r\n` pair, and a bare `\n`), `packages/tui/ink-ui/tests/components/Composer.spec.tsx`'s `REGRESSION: text and Enter delivered in ONE stdin write still submit and clear the composer` (a single `stdin.write('hello\r')`, unlike every other test in that file, which deliberately splits the text and `\r` into two writes), and `packages/tui/runtime/tests/pty-smoke.client.spec.ts`'s second scripted turn, sent as `shell.write('bundled prompt\r')` in one call over a real pty — reusing the same booted session as the file's existing split-write turn (a second full Loader boot in the same file was measurably more prone to timing out under host load) — asserting the scripted reply streams and the composer ends up empty.

Every other `useInput`-driven input path in this package (`ApprovalPrompt`, `QuestionPrompt`) takes single-character `y`/`n`/digit input only and was not touched; a future multi-character input surface on either would need the same merged-run handling this Agent Note describes if it accepts free text.
