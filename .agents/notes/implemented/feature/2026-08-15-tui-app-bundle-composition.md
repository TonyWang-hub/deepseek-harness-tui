# Agent Note: `dsh --profile tui` shipped composition (D2.3)

Status: implemented

English | [中文](2026-08-15-tui-app-bundle-composition.zh.md)

## Problem

`packages/tui/runtime` (D2.1) bootstrapped the dual-context Client tree and `packages/tui/ink-ui` (D2.2) shipped the terminal renderer over it, but no shipped composition mounted either package: `dsh --profile tui` did not exist in `PROFILE_TEMPLATES`, nothing owned turning `mountTuiRenderer`'s exit into a process exit, and `--resume` had no command-line surface. The D2.2 Agent Note named this gap explicitly as its own last deferred item, and the removal record for the previous terminal frontend ([2026-08-04](../simplification/2026-08-04-remove-tui-package.md)) requires a shipped composition before a terminal package counts as reintroduced.

## Decision

`packages/bundle/tui-app` (`@deepseek-ai/dsh-tui-app`) is the fourth shipped bundle, alongside `dsh-base`, `dsh-web-app`, and `dsh-headless`. `PROFILE_TEMPLATES.tui` (`packages/boot/app-boot/src/profile.ts`) is `['@deepseek-ai/dsh-base', '@deepseek-ai/dsh-tui-app']`; `dsh --profile tui` auto-initializes from it exactly like `web` and `headless`.

`cordis.patch.yml` rides over `dsh-base` unchanged in its agent plane — base already composes the agent process-wide (the same posture headless keeps), so this bundle adds only the rows a terminal composition needs beyond base: the storage/workspace/directory-picker rows `ApiProxyService.inject` requires but base does not itself mount, `tool-ask-user` (shipped in every agent preset but never at base's own top level), the API gateway, Connection's Host half (`trustedHosts: []`, no listening socket to trust), this bundle's own `tui-startup` command-line provider, the `tui-runtime` row, and this bundle's own `tui-runner` process owner. The Web surface's disable list (`tool-bash`, `skill-filesystem`, `plan-mode`, subagents, …) does not apply here: that list exists because Web moves the agent plane behind per-session presets, which the terminal composition does not do.

`tui-runner` (`src/index.ts`) is the one plugin that decides what the process does once `ctx.tuiRuntime` is ready. `inject: ['tuiRuntime']` is a plain string, so cordis suspends `apply()` until the row provides the service with no TypeScript merge required — the service itself is read through the package-local narrow structural type `TuiRuntimeLike` (`{ renderer?: { waitUntilExit(): Promise<void> } }`) and `ctx.get('tuiRuntime')`, never a static import of `@deepseek-ai/dsh-tui-runtime` or `@deepseek-ai/dsh-tui-ink-ui`. Both of those type-check under the CLIENT aggregate (their own `tsconfig.client.json`), while `dsh-tui-app` type-checks under the HOST aggregate beside `dsh-headless` and `dsh-web-app` — the same Host/Client cross-merge hazard `dsh-tui-runtime`'s own module doc documents one layer down for `ctx.connection`, avoided here the identical way. A real TTY mounted a renderer (`tui-runtime`'s own `Config.render`, default `true`, gated on `process.stdout.isTTY`): `tui-runner` awaits `renderer.waitUntilExit()` and requests process exit through the launcher-provided `ctx.appExit`. No renderer mounted (a piped, CI, or otherwise non-interactive invocation) is a genuine misconfiguration for this profile — nothing else in the composition would ever produce output or exit — so `tui-runner` fails loud instead of hanging forever, the one behavior `tui-runtime` deliberately does not itself provide (it silently skips mounting under a non-TTY `stdout`, correct for a package a test harness also composes).

`--resume <sessionId>` is this bundle's own `tui-startup` provider (mirroring `headless-startup`/`web-startup`): it injects `cmdlineArgs`, parses the flag and this app's `--help`, and provides `tuiStartup` with no declared `Context` merge (matching `headlessStartup`/`webStartup`'s own precedent — a plain `ctx.provide()`, invisible to the `SERVICE_PAGE`/`SERVICE_WALK_EXEMPTIONS` catalog scan, which walks only declared `Context` merges). `tui-runtime`'s `Config` gained one field, `resumeSessionId?: string`, wired from the row's own `!!js ctx.tuiStartup.resumeSessionId` expression; `apply()` brands it into `MountOptions.sessionId` at the single point that reads it (the same "compile-time cast, no runtime cost" contract `SessionId()` documents). `mountTuiRenderer`'s own MVP limitation carries through unchanged: a resumed session's prior nodes are the committed baseline and are never replayed into scrollback.

The real-composition acceptance test (`packages/bundle/tui-app/tests/pty-smoke.spec.ts`) boots the shipped composition through `loadProfile`/`healProfilesModuleFallback`/`boot` (`@deepseek-ai/dsh-app-boot`) — the exact production profile-resolution path, exercising `PROFILE_TEMPLATES.tui` directly rather than an ad-hoc row list — under a real pty, with a scripted `dsh-llm-replay` turn installed post-boot on the settled context (mirroring `apps/web/tests/scaffold.ts`'s own pattern, not `packages/tui/runtime/tests/compose.client.ts`'s Client-aggregate reimplementation, since this package's tests type-check under the HOST aggregate and can import `dsh-app-boot` and `dsh-llm-replay` directly). It reuses `packages/tui/runtime/tests/pty-smoke.client.spec.ts`'s exact marker protocol and `stty -a` restoration check.

## Alternatives considered

**Have `tui-runner` call `mountTuiRenderer` itself, disabling `tui-runtime`'s own auto-mount** — rejected: it would require `dsh-tui-app` to statically import `@deepseek-ai/dsh-tui-ink-ui` for `mountTuiRenderer`/`MountOptions`, pulling that package's Client-aggregate Context merges (`connection`, `sessions`) into the Host-aggregate program `dsh-headless` and `dsh-web-app` already share — the exact hazard `dsh-tui-runtime`'s own module doc warns against one layer down. Reading `ctx.tuiRuntime` through a local structural type and letting `tui-runtime` keep owning the mount (as designed) needs no such import.

**Give `dsh-tui-app` the same preset-plane disable list as `dsh-web-app`** — rejected: that list exists because Web moves the agent plane behind per-session presets; the terminal composition has no preset plane and keeps the agent process-wide, the same posture `dsh-headless` already has. Copying the disables would silently remove tools and prompt sections the terminal composition is documented (by `compose.client.ts`'s own comments) to need enabled.

**Model the real-composition test on `compose.client.ts`'s ad-hoc row list instead of the real bundle patch** — rejected: `compose.client.ts` exists specifically because `packages/tui/runtime`'s own tests type-check under the Client aggregate and cannot import `dsh-app-boot` (a Host package) without poisoning that program. `dsh-bundle/tui-app`'s tests carry no such constraint, so booting through `loadProfile`/`PROFILE_TEMPLATES.tui` and the real `cordis.patch.yml` is strictly more faithful evidence for "the shipped bundle patch works," and exercises the `PROFILE_TEMPLATES` change directly.

**Give `tui-runtime`'s row an explicit `inject: ['apiProxy']` ordering dependency to close the boot-order hazard the D2.2 Agent Note's Consequences section named** — rejected for this cut: the hazard is proven to reproduce only under fast in-process Loader-driven test timing, not the pty smoke's real, slower process timing (the D2.2 note's own finding). Fixing it is out of D2.3's scope; the real-composition test uses the same real-pty technique that already avoids it, so this cut ships no unproven ordering fix.

## Consequences

`dsh --profile tui` is a real, working product entry point: a person runs `pnpm dsh --profile tui` and gets a working terminal session — prompt, streaming, scrollback commit, Ctrl-C exit with the terminal restored — proven by a real pty smoke through the actual shipped bundle patch, not a test-only composition. `--resume <sessionId>` opens an existing session (no backfill, matching the renderer's own MVP limitation, documented in this package's own README).

`packages/tui/runtime`'s `Config` gained `resumeSessionId` as a small, backward-compatible addition (defaulting to absent, unchanged behavior for every existing consumer and test).

Known deferred work carried into a later cut: the boot-order hazard between `tui-runtime`'s own `apply()` and `api-gateway`'s route registration (named in the D2.2 Agent Note's Consequences) is unresolved; `/history`, tail rebase, and the long-session performance gate are the official-terminal-application Agent Note's own later landing-order items, not this cut's.
